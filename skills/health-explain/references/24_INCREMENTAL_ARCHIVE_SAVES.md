# Incremental archive saves and recovery

Operational workflow for an owner-authorized archive. This module changes persistence decisions, not clinical interpretation. Actual conversations, timings, identifiers, receipts and error traces remain private. The optional planner uses local files only; it supplies no connector, lock, background process or automatic synchronization.

## Choose the operation before loading the archive

Distinguish a new archive/full rebuild from a small conversation update, a source correction, a status check and recovery of an unfinished operation. Complete-view defaults in module 23 apply to setup or a requested rebuild; they do not require downloading and rewriting every view after each reply. Reuse the configured authoritative ledger, managed file IDs and generation rules. Never create a second ledger because an older instruction prefers Sheets.

For a small update, read current configuration, the relevant accepted rows and the operation journal. Refresh the current medication/allergy facts needed for the answer; an older prose summary may contain superseded uncertainty. Later explicit owner corrections supersede the mistaken interpretation through reviewed provenance, while the old wording remains in history. Distinguish the owner's observation from a causal claim. Do not derive a condition from a medicine or turn an ambiguous voice transcription into a fact. Date expressions describing age, calendar year and relative time retain their original meaning and uncertainty.

Load only generators, sources and views needed for the change. Use privately recorded IDs and content/version hashes to avoid repeated folder discovery and duplicate attachment processing. Cached material is reusable only against its current remote version; missing configuration triggers bounded discovery, not guessed paths or table names. Inspect the actual database schema and configured adapter before querying or staging rows.

## Commit facts, then refresh affected views

1. Preserve the available source and stage a delta using stable operation/row IDs. If the owner requests the conversation itself, save the accessible messages with roles/order and an explicit coverage statement. A medical summary is not a verbatim transcript. Never reconstruct unavailable messages or claim complete chat access.
2. Serialize writes to the authoritative ledger. Back it up, merge with its current version and apply module 20's commit/readback rules. A local SQLite transaction does not lock the remote blob. A version reread is detection, not compare-and-swap. If another writer changes the base, reconcile against the new version before upload; do not replace it with the older copy.
3. Record separately whether the source, ledger and requested reader views were verified. A saved supplement is pending integration until accepted ledger rows exist. It must not be presented as complete ledger persistence.
4. Generate affected views using the existing private commands. Compare generated bytes with the previously verified content hashes and upload only changed managed outputs. Preserve owner answer cells, comments and unrelated files. Essential summaries must reflect the committed facts. If a requested view cannot be updated, report it as pending; do not silently reduce the requested scope.
5. Read back changed material values or bytes and the final journal marker once. Reuse verified evidence within the operation unless a write, version change, failure or inconsistency invalidates it. A successful upload response alone is not readback; repeated downloads of unchanged files add no evidence.

Do not patch/archive generators, redesign the layout, rebuild unrelated laboratory previews or migrate the schema as an incidental small save. If an incompatible generator actually prevents required views, scope the repair explicitly and preserve the original. New facts and their persistence status should remain visible while a repair is pending.

## Bounded recovery

Use the connector's authenticated file reference or materialized workspace path for raw files, after inspecting MIME metadata. A preview/text extraction is not original-byte storage. Do not assume a returned HTTPS bearer URL is usable by the shell or make it public. If the authorized file route fails, retain staged content and the verified state, and report the missing step. Do not invent an unavailable materializer.

For a transport error or timeout, inspect the operation/file/row IDs before one targeted retry. For a permission or HTTP 403 error, check the supported file route and permissions; repeating the same request indefinitely is not recovery. A new retry is justified by changed evidence, such as a corrected argument or refreshed authenticated reference. Avoid arbitrary user-agent guessing and dumping large binary/base64 content into commands or model output. Write payloads through file tools; use available standard-library code rather than assuming optional packages exist.

On an unknown upload outcome, read the exact remote target before deciding whether to retry. Retain original IDs and the same operation journal. Do not create duplicate supplements, regenerate all rows or discard successful work. A failed readback leaves an unverified result, not a verified hash. The optional planner emits `inspect_remote` for uncertain prior outcomes; it never resolves them by itself.

## Report status and measure the delay

Use precise statements: source preserved; supplement saved; ledger committed and read back; views updated and read back; or partial, with named pending steps. Reading a skill is not proof of saving. A local staging link is not the selected remote archive. A status check should reuse the verified receipt and inspect only unresolved evidence; do not perform a new import when nothing changed.

Bind every receipt to this archive and this operation's source/delta fingerprint, row IDs and remote version. An earlier completed receipt does not prove that a new conversation update was saved. Reconcile changed versions and verify coverage before reusing receipt evidence.

Keep private stage timestamps, call counts, bytes transferred, retries and reasons for regeneration. Separate elapsed turn time from recorded tool durations; calls can overlap and gaps cannot be attributed to a service from these logs alone. Do not promise an unmeasured time target or a platform-level fix. Progress updates should name the completed persistence stage and the remaining blocker.

The optional `scripts/plan_archive_sync.py` under the import skill compares explicitly managed local files against a private verified sync state. It stages a plan only, with no network, writes to the archive, deletions or concurrency guarantees. The adapter must check remote versions, execute authorized writes and populate verified state from readback.
